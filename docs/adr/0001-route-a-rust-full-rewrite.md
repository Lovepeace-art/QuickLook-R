# ADR-0001：采用路线 A —— Rust 全量重写，插件生态后续重建

- 状态：已采纳
- 日期：2026-10-29
- 相关：`docs/route-a-plan.md`、`docs/route-a-wbs.md`、`docs/bench-compare.md`（仓库上级）

## 背景

QuickLook 是 C#/WPF + 25 个托管插件（插件 44,775 LOC、宿主 6,471 LOC）。同机实测的差距是结构性的：

| 场景 | QuickLook 4.5.0 | Rust 原型 | 差距 |
|---|---|---|---|
| 4K JPEG 热路径 | 421 ms | 10 ms | 42× |
| 48MP JPEG 热路径 | 418 ms | 44 ms | 9.5× |
| 26.6 MB 文本热路径 | 923 ms | 12 ms | 77× |
| 常驻空闲内存 | 96 MB | 5–8 MB | ~12× |
| 分发体积 | 122.5 MB | 0.27 MB | ~450× |

三条候选路线：A 全量重写（生态后续重建）；B 混合（Rust 宿主 + 托管插件桥）；C 只做高频格式子集。

## 决策

走 **路线 A**：Rust 从零实现宿主与格式渲染，插件体系在 M5 用**进程外协议**重建，不兼容现有 .NET 插件二进制。

## 理由

1. **B 的技术底子不稳**：托管插件是 WPF 类库，必须 STA 线程 + 自己的 HWND，只能通过 `netcorehost`（hostfxr）拉起来。这等于把 WPF 的生命周期重新塞回 Rust 宿主，冷启动与内存收益大半被吃掉，还多一层 ABI 风险。
2. **C 会卡在"换不掉"**：QuickLook 的真实使用面覆盖 307 个扩展名，只做子集等于让用户在两个工具间来回切，不如不做。
3. **上游自己也认为隔离是方向**：CHANGELOG 未发布段有 "Add COM wrappers and out-of-proc preview host [#1929]"。
4. **收益天花板已经量出来了**（上表），剩下的是工程量问题，不是可行性问题。

## 后果

- 必须承担格式覆盖的完整成本：WBS 给出基线 **乐观 13.1 / 中位 19.8 / 悲观 28.8 人月**（S1 功能对齐档 + A8 性能专项）。单人全职到"可日常替换"约 8–9 个月。
- 现有 QuickLook 用户安装的 `.qlplugin` 插件**不能直接用**（M5 才提供新的插件形态）。
- Office 一类"没有纯 Rust 保真方案"的格式，明确走系统 `IPreviewHandler`（依赖本机 Office）或外挂 LibreOffice，不自研。

## 备选与否决理由

- **B 混合**：省 40% 工时但吃掉主要收益，且 STA/WPF 桥的失败模式不可控。
- **C 子集**：工时 6–8 人月，但无法替代现有工具，用户迁移意愿低。
- **不改语言，只优化 QuickLook**：热点在原生（WIC/DirectWrite/MF/COM `prevhost.exe` 冷启 7–8 s），换语言≈0 收益的判断反过来也成立——不换语言同样改不动这些热点。
