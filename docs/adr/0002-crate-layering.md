# ADR-0002：三 crate 分层，`qlr-core` 不依赖 `windows`

- 状态：已采纳
- 日期：2026-10-29
- 相关：`docs/dev/ARCH.md` §1

## 背景

Windows 桌面程序的自然写法是"一个 bin crate 从头到尾"，但这样会遇到三个具体问题：

1. **测试只能靠跑起来看**：一旦逻辑和 FFI 混在一起，纯逻辑（配置钳制、路径判定、IPC 编解码、日志格式）也得开真窗口才能验。
2. **FFI 与业务判断纠缠**：失败降级策略（托盘失败是否致命、亚克力不可用怎么办）散落在各处，接手者看不出"哪些是可降级的"。
3. **热路径被静态链接拖累**：解码器/渲染器的重依赖一旦进了主 crate，冷启动就带着它们一起进内存（A8.5 装载裁剪要靠分 crate + 延迟加载实现）。

## 决策

三个 crate，依赖方向单向：

```
qlr-app ──► qlr-platform ──► qlr-core
   └──────────────────────────▲
```

- `qlr-core`：**禁止** `windows` 依赖，可跨平台 `cargo test`。
- `qlr-platform`：只做 FFI 薄封装，返回 `windows::Result`/`Option`，**不做业务决策**。
- `qlr-app`：业务判断、状态机、降级策略。

## 理由

- 当前 25 个单测里有 16 个（core 13 + platform 3 的纯函数）**不碰窗口就能跑**，这是回归速度的关键。
- 降级策略集中在 app 层，一眼能看出"哪些失败只 WARN"：托盘、亚克力、DPI 都是降级；只有"注册窗口类失败"是致命。
- 未来把解码器放进 `qlr-decode`、渲染放进 `qlr-render` 时，依赖方向已经定好，不需要重排。

## 后果

- 多两个 crate 的编译单元，`cargo build` 略慢（实测 release 全量 15.6 s，可接受）。
- platform 的函数签名必须"薄"，不能顺手在里面写业务逻辑——这是纪律，靠 review 保证。
- `HWND` 不是 `Send`，跨层进全局状态时必须在 app 层包一层 `Hwnd(isize)`。

## 备选

- **单 crate 多 module**：启动最快，但上面三个问题都存在，且将来做装载裁剪要重构。
- **core/platform 合并**：省一个 crate，代价是 core 的跨平台单测全部丢失。
