## 1. ③ 连续滚动评估

### 现状
- 文本/Markdown（`Canvas::Text`）：**本就是连续滚动**（`s.scroll` 按行累积，`scroll_info` 返回行位置）。
- docx/pptx/pdf（`Canvas::Document/Presentation` + pdf）：**翻页式**——`State.page` 只存页码，`paint_page`/`paint_slide` 通过 `page_transform(content, page_w, page_h)` 把“当前一页”缩放居中画到内容区；`scroll_info` 对 docx/pptx 走 `pages` 分支（页码/总数），滚轮/PageUp·Down 改页码。
- 关键前提：docx/pptx 的**完整模型已在内存**（`DocDoc{ pages }` / `PptxDoc{ slides }`），翻页不重新解析。pdf 才走页缓存。

### 目标语义（若做）
纵向连续：把所有页按 `page_h` 依次堆叠，内容区显示一个垂直窗口；滚轮/滚动条按“全局像素”平移，跨页边界自然连续；页码框显示“当前视口顶部所在页”。

### 方案（改动面）
1. `qlr-app::session` 的 docx/pptx 会话增加 `view_y: f64`（全局像素偏移）。
2. `qlr-app::chrome::scroll_info`：docx/pptx 从“页码”改为“像素比例”（`view_y / (total_h - view_h)`），与 pdf 区分。
3. `qlr-platform::window::docx/pptx` 的 `paint_page`：由“只画第 `page` 页”改为“画 `view_y..view_y+view_h` 覆盖到的所有页”，逐页 `translate` 后画；裁剪到内容区。渲染成本 ≈ 可见页数 × 单页绘制（视口高度 1–3 页，单页已 ~1–3ms）→ 每帧仍 < ~10ms。
4. `qlr-app::input`：滚轮不再 `step_page`，改为按像素平移（`scroll_by_px`）；PageUp/Down 仍按“一屏高度”翻（= `view_h`）。
5. 页码框：`current = page_at_y(view_y)`。

### 成本 / 风险
- 成本：docx + pptx 各约 2–3 人日（pdf 可复用同套 `view_y`，但 pdf 有页缓存需配合预取）。
- 风险：① 每帧多画 1–3 页，滚动时 CPU 略升（仍远低于渲染引擎，且只画可见页）；② 页码框语义从“第 N 页”变“顶部页”，需与用户对齐；③ 与“对比模式”多窗口共用 `State`，要确保 `view_y` 进每窗会话（已是按窗口会话，天然满足）。
- 内存：**模型本就在内存，连续滚动不增加模型内存**；只是丢弃“仅当前页像素”的假设——但当前也是按帧重画，不是缓存整页位图，所以内存基本持平。

### 结论（建议）
**值得做，但优先级低于 ④ 的“确定性 bug 修复”。** 连续滚动主要是“体验更好”，非“更准/更快”。建议放在 ①②④ 稳定之后、⑤ 之前。若做，先 docx（契约/报告多为长文档），pptx 次之。

## 3. ⑤ 进程外沙箱评估

### 现状与风险
- 现在所有解析/绘制都在宿主进程内，且 release `panic=abort`。畸形文件理论上可致 panic → 整个应用退出（已用 `MAX_*` 上限 + 越界/畸形单测/fuzz 兜底，实测 broken/fake 优雅失败，未见崩溃）。
- ADR-0010“进程外沙箱”当初**暂缓**：每格式开子进程 + 跨进程传位图/窗口，复杂度高。

### 方案与成本
- 方案 A：渲染子进程（子进程 parse+绘制到 DIB，经共享内存/IPC 回传 BGRA 给宿主窗口贴图）。成本高（3–5 人日/格式，含 IPC、生命周期、超时）。
- 方案 B：仅“解析”隔离（子进程只 parse 成模型序列化回传，绘制仍在宿主）。收益有限，序列化成本高。
- 方案 C（务实）：维持 in-proc，**强化防御**——扩展 fuzz 语料（畸形 zip/XML/超深嵌套/超大数值）、统一 `catch_unwind`（需 panic≠abort，与现设置冲突）、补输入上限。成本低。

### 结论
**不建议现在做 A/B**（收益/成本比差，且当前没有实际崩溃证据）。建议维持 in-proc + 持续补畸形测试（C）。若未来出现真实崩溃样本，再按方案 A 单点隔离最危险的那个格式。
