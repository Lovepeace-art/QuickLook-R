# 基准（BENCH）

> 采集脚本：`scripts/bench.ps1`（结果同时写 `scripts/bench-results.json`）
> 采集环境：Windows 10 19045 / i5-12400F / 15.9 GB RAM / release 构建
> 对照基线：上级目录 `docs/bench-compare.md` 里同机同夹具的 **QuickLook 4.5.0** 数字

## 1. 口径

| 列 | 含义 |
|---|---|
| `RenderMs` | worker 线程里 `qlr_render::render_file` 的耗时（日志 `RENDER … elapsed=`） |
| `PerceivedMs` | 从"第二实例投递请求"到"日志出现 RENDER"的墙钟时间：含进程创建、`WM_COPYDATA`、窗口显示 |
| `PeakRSSMB` | 渲染过程中的采样峰值（**不是**事后读到的稳态；解码完缓冲就释放了） |
| `RSSMB` / `PrivateMB` | 预览完成后的稳态 |

## 2. 当前数字（A2.3 之后：JPEG 走 DCT 域缩放解码）

| 场景 | RenderMs | PerceivedMs | PeakRSS | 稳态 RSS | 产物字节 |
|---|---|---|---|---|---|
| 4K 3840×2160 JPEG | 32–34 | **50–57** | 11.7–24.8 | 11.7 | 3,184,440 |
| 48MP 8000×6000 JPEG | 66–69 | **81–98** | **11.5–12.8** | 11.5 | 2,983,024 |
| 26.6 MB 文本 | 22 | **34–35** | 11.6–12.9 | 11.6 | 130,890 |

（第 2 轮为热路径。`PeakRSS` 是采样值，采样间隔 8 ms，偶尔会漏掉瞬时高点——所以看量级不看小数点。）

### 与 A2.3 之前对比（同一脚本、同一机器）

| 场景 | RenderMs 前 → 后 | 峰值 RSS 前 → 后 |
|---|---|---|
| 4K | 57–62 → **32–34**（−45%） | 34.2 → **11.7**（−66%） |
| 48MP | 171–175 → **66–69**（−61%） | 148–150 → **12.8**（**−92%**） |

48MP 的峰值从 150 MB 掉到 12.8 MB，是因为 `jpeg-decoder` 按 1/8 直接把 8000×6000 解成 1000×750
（3 MB），中间从不产生 192 MB 的整图缓冲——这就是 A2.3 的核心收益，**已达 A8.1 的 ≤60 MB 预算**。

## 3. 与 QuickLook 4.5.0 同机对拍

| 场景 | QuickLook 热路径 | QLRust 感知延迟 | 倍数 | QuickLook 峰值内存 | QLRust 峰值 | 倍数 |
|---|---|---|---|---|---|---|
| 4K JPEG | 421 ms | 50–57 ms | **7–8×** | 225 MB | 11.7–24.8 MB | **9–19×** |
| 48MP JPEG | 418 ms | 81–98 ms | **4–5×** | 404 MB | 11.5–12.8 MB | **31–35×** |
| 26.6 MB 文本 | 923 ms | 34–35 ms | **27×** | 224 MB | 11.6 MB | **19×** |

## 4. 这些数字说明了什么

1. **高频路径（4K 图、普通文本）已经进入"感觉不到"的区间**（<100 ms），继续压毫秒对用户无价值。
2. **48MP 已达标**：A2.3 用 `jpeg-decoder` 的 DCT 域缩放（1/8 档）直接解到 1000×750，
   峰值从 150 MB 降到 12.8 MB、RenderMs 从 171 降到 66——**远低于 A8.1 的 ≤60 MB 预算**。
   剩下的优化空间只有"首屏 ≤25 ms"，那属于后台精修（先出 1/8 预览，再异步补细节）。
3. **文本的 27× 不是我们多快，是 QuickLook 在文本上做了很蠢的事**（整文件读入 + AvalonEdit 全文排版）。
   我们靠"8 MB 读入上限 + 只保留 2000 行"就赢了，这也解释了它当年为什么会吃掉 6.6 GB。

## 5. 还没量到的

- **冷路径**：脚本每轮都重启常驻实例，但 PerceivedMs 量的是"常驻实例处理请求"，不含冷启动。
  冷启动单独看 `smoke.ps1` 的 `冷启动并进入壳层`（当前 71 ms）。
- **PDF / 视频 / Office**：还没实现（A2.6 / M4 / M3）。
- **连续翻页（预取）**：M2 不做，A8.2 的 daemon + A9.4 的预取再量。

## 6. 复现

```powershell
cargo build --release
pwsh -NoProfile -File scripts/bench.ps1 -Exe target\release\qlrust.exe
```

脚本会自己找夹具（仓库内 `spike\fixtures` → 上级 `spike\fixtures`），每轮重启常驻实例，
跑完把 JSON 写到 `scripts/bench-results.json`。**任何性能改动都必须贴前后两组数字再合并**（AGENTS.md §4）。

## 7. PDF（A2.6，0.1.6）

夹具：`_bench/pdfium/test-200page-word.pdf`（Word 导出，200 页，228,310 B），窗口 1190×748。
口径：`qlrust.exe --render <pdf> --page N` 无窗口渲染，取日志里的 `elapsed`（含打开文档 + 渲染 + 转 BGRA）。

| 页 | 0 | 1 | 50 | 100 | 150 | 199 |
|---|---|---|---|---|---|---|
| RenderMs | 9 | 4 | 6 | 5 | 8 | 6 |

- **平均 6.3 ms、最慢 9 ms**（WBS 验收线"1000 页 PDF 翻页 ≤80 ms"，本夹具页数只有 200，
  但打开文档的固定开销已在每次测量里，翻页本身是 1–3 ms）。
- 端到端（常驻实例翻页）：`PAGE 2/3` → `RENDER gen=2 … 2ms`，即**按 PageDown 到新页上屏约 2–3 ms**。
- 未量：大页面（A3/A0 图纸）、带图片扫描件的 PDF、加密 PDF、损坏 PDF 的内存峰值。

## 8. PDF 缩放后的渲染耗时（0.1.7）

| 场景 | 请求尺寸 | 位图 | 渲染 | 备注 |
|---|---|---|---|---|
| 3 页测试 PDF，原尺寸 | 1190×748 | 529×748 | 5 ms | 整页可见 |
| 放大到 125% | 1488×935 | 661×935 | 2 ms | 矢量重栅格化 |
| 放大到 156% | 1859×1169 | 826×1169 | 2–3 ms | 仍远快于 WBS 的 ≤80 ms 线 |

200 页 Word PDF：翻页取 0/1/50/100/150/199 页，**均值 6.3 ms、最慢 9 ms**。

## 9. 0.2.0（文本折行后）复测 —— 手工流程

`scripts/bench.ps1` 本轮不稳定（见 CONVENTIONS #37），以下用手工流程测：宿主放工作目录外
（`D:\qlrust-bench`，保证 High 完整性），每夹具先 `--quit` 老宿主、清日志、起宿主、投文件、
轮询进程采样峰值、再读 `RENDER` 行。

| 场景 | RenderMs | 感知 ms | 峰值 RSS | 备注 |
|---|---|---|---|---|
| 3840×2160 JPEG | 41 | 87 | 12.5 MB | 请求 1190×748，位图 1190×669 |
| 8000×6000 JPEG | 77 | 95 | 12.3 MB | JPEG DCT 缩放解码 |
| 26.6 MB 文本 | 21 | 53 | 21.7 MB | 121,425 行；折行只算当前屏 |

对照 0.1.9（折行前）：4K 32–34 ms / 48MP 66–69 ms / 文本 21 ms —— 折行没有引入明显额外开销
（文本那点差异在噪声内，折行只处理一屏 30 行）。

## 10. 1.0.14 vs QuickLook 4.5.0 同机横向对比（2026-10-31）

完整报告在工作区 `docs/bench-vs-quicklook-1.0.14.md`，复现脚本 `_bench/cmp-1014.ps1`。
口径是**纯外部观测**（`EnumWindows` 轮询等可见窗口 + `WorkingSet64` 采样），两边同一套代码。

| 指标 | QuickLook 4.5.0 | QLRust 1.0.14 | 倍数 |
|---|---|---|---|
| 冷启动首帧（4K / 48MP / 27 MB 文本 / PDF / MD） | 1170 / 1100 / 1828 / 1170 / 1130 ms | **41 / 41 / 40 / 39 / 39 ms** | 27–46× |
| 热路径首帧（同上） | 473 / 385 / 1179 / 416 / 420 ms | **17 / 16 / 40 / 16 / 16 ms** | 24–29× |
| 常驻空闲 | 95 MB RSS / 98 MB private / 20 线程 / 518 句柄 | **8.8 MB / 1.8 MB / 6 / 149** | 10.8× / 54× |
| 48MP 预览峰值 | 404 MB | **16 MB** | 25× |
| 关掉预览之后 | 162–414 MB（不回落） | 11–27 MB（回落） | 15–20× |
| 分发物 | 1481 文件 / 276.9 MB / 需 .NET 4.8 | **6 文件 / 9.2 MB / 零运行时** | 30× |

两边空闲 CPU 增量均为 0.000 s/6 s；GDI 对象 14 vs 16（同量级，都不漏）。
结论与优化建议（投机预渲染、GPU 呈现、PDF 分块 + 页缓存、渲染超时与崩溃兜底、长稳压测）见该报告第 5–6 节。
